Quando um dado muda em vários lugares

Imagine que o telefone de uma cliente esteja copiado em várias linhas de uma planilha. Quando o número muda, precisamos corrigir cada cópia; se uma passar despercebida, os registros entram em conflito. Essa falha é uma anomalia de atualização, causada por redundância.

Normalização é o processo de organizar tabelas e suas relações para reduzir redundâncias e anomalias sem perder a informação. Vamos acompanhar exemplos antes de apresentar cada regra e ver quando separar uma tabela ajuda — e quando uma decomposição exige cuidado [1][2].

Aprofundamento: vocabulário essencial

Relação e atributo
Relação é uma tabela; atributo é uma coluna dessa tabela.
Chave primária (PK)
Coluna ou conjunto de colunas escolhido para identificar cada linha sem repetição e sem valor nulo.
Chave estrangeira (FK)
Coluna ou conjunto de colunas que referencia uma chave de outra tabela, mantendo a relação entre os registros.
Dependência funcional (X → Y)
Regra segundo a qual um valor de X determina um único valor de Y em todos os registros válidos.
Valor atômico e atributo primo
Valor atômico é um único valor indivisível para o uso definido; atributo primo é aquele que participa de ao menos uma chave candidata.
Chave candidata e superchave
Uma chave candidata identifica cada linha e não possui atributos desnecessários; uma superchave também identifica cada linha, mas pode conter atributos extras.
Dependência multivalorada (X ↠ Y)
Regra que associa a cada valor de X um conjunto de valores de Y independente dos demais atributos da relação.
Dependência de junção
Regra que permite decompor uma relação em projeções e reconstruí-la pela junção dessas projeções, sem gerar tuplas espúrias.
Junção (JOIN)
Operação que combina linhas de tabelas relacionadas conforme uma condição comum.
Decomposição sem perda
Separação de uma relação em tabelas menores cujas junções recuperam exatamente os registros originais, sem perder linhas nem criar combinações falsas.

Definições formais, em uma camada a mais

  • 1FN: cada atributo contém um valor do seu domínio por linha; não armazenamos listas em uma única célula.
  • 2FN: a relação está na 1FN e todo atributo não primo depende funcionalmente de cada chave candidata em sua totalidade, sem depender de apenas uma parte.
  • 3FN: para toda dependência funcional não trivial X → A, X é superchave ou A é atributo primo.
  • FNBC: para toda dependência funcional não trivial X → Y, X é superchave.
  • 4FN: para toda dependência multivalorada não trivial X ↠ Y, X é superchave.
  • 5FN: toda dependência de junção não trivial é implicada pelas chaves candidatas da relação.

Endereço e telefones: quando uma célula guarda mais de um dado

O problema antes da regra

A tabela abaixo guarda endereço composto em uma coluna e mais de um telefone na mesma célula. Isso dificulta filtrar por cidade e localizar ou atualizar somente um telefone.

Cadastro original com valores agrupados
IDNomeEndereçoTelefones
1Ana SouzaRua das Flores, 100, Centro - São Paulo/SP(11) 98765-4321, (11) 91111-2222
2Carlos SilvaAv. Paulista, 500, Bela Vista - São Paulo/SP(11) 93333-4444

O que exige a Primeira Forma Normal (1FN)

Vamos reorganizar os dados para que cada atributo contenha um valor atômico no contexto do domínio e que não se armazenem listas em uma célula. “Atômico” não significa que todo texto deva ser dividido ao máximo: endereço pode ser um único atributo se a aplicação não precisar tratar suas partes separadamente. Se logradouro, bairro, cidade e UF forem consultados independentemente, faz sentido representá-los como atributos próprios.

Clientes com atributos de endereço separados
ID clienteNomeLogradouroBairroCidadeUF
1Ana SouzaRua das Flores, 100CentroSão PauloSP
2Carlos SilvaAv. Paulista, 500Bela VistaSão PauloSP
Telefones: um número por linha
ID telefoneID cliente (FK)Número
11(11) 98765-4321
21(11) 91111-2222
32(11) 93333-4444

A tabela de telefones se relaciona a clientes pela chave estrangeira. Assim, cada número pode ser consultado e atualizado sem manipular uma lista textual.

Exemplo SQL: clientes e telefones

Dialeto: SQLite 3.53.3. O exemplo foi testado em banco em memória.

-- Criamos as tabelas separadas e relacionamos o telefone ao cliente.
PRAGMA foreign_keys = ON;

CREATE TABLE clientes (
  id_cliente INTEGER PRIMARY KEY,
  nome TEXT NOT NULL
);

CREATE TABLE telefones (
  id_telefone INTEGER PRIMARY KEY,
  id_cliente INTEGER NOT NULL,
  num_telefone TEXT NOT NULL,
  FOREIGN KEY (id_cliente) REFERENCES clientes (id_cliente)
);

-- Inserimos um cliente e dois telefones, um por registro.
INSERT INTO clientes (id_cliente, nome) VALUES (1, 'Ana Souza');
INSERT INTO telefones (id_telefone, id_cliente, num_telefone)
VALUES (1, 1, '(11) 98765-4321'), (2, 1, '(11) 91111-2222');

-- Consultamos cada número sem separar texto manualmente.
SELECT c.nome, t.num_telefone
FROM clientes AS c
JOIN telefones AS t ON t.id_cliente = c.id_cliente;

Consulte a documentação oficial do SQLite para CREATE TABLE [4].

Matrículas: dados repetidos em uma chave composta

Exemplo antes da definição

Considere a tabela de matrículas. A combinação (ID_Aluno, ID_Curso) identifica uma matrícula, mas os nomes de aluno e curso se repetem:

Matrículas com dados repetidos
ID alunoID cursoNome alunoNome curso
1101AnaBanco de Dados
1102AnaProgramação
2101PedroBanco de Dados

Regra da Segunda Forma Normal (2FN) e decomposição

Vamos separar os dados de aluno e curso da matrícula. Uma relação está na 2FN quando está na 1FN e cada atributo não primo depende funcionalmente de cada chave candidata em sua totalidade, sem depender apenas de parte de uma chave composta. Neste exemplo, Nome_Aluno depende de ID_Aluno e Nome_Curso depende de ID_Curso; são dependências parciais [2].

  • Alunos: ID_Aluno (PK), Nome_Aluno.
  • Cursos: ID_Curso (PK), Nome_Curso.
  • Matrículas: ID_Aluno (PK, FK), ID_Curso (PK, FK).

Assim, registramos cada nome uma vez em sua tabela e mantemos em Matrículas apenas o relacionamento entre alunos e cursos.

Funcionários e departamentos: redundância em cadeia

Exemplo de redundância

Em uma tabela de funcionários com (ID_Funcionario, Nome, ID_Departamento, Nome_Departamento), o nome do departamento se repete para cada funcionário da mesma equipe.

Funcionários antes da decomposição
ID funcionárioNomeID departamentoNome departamento
1Ana10Financeiro
2Bruno10Financeiro
3Caio20Vendas

Regra da Terceira Forma Normal (3FN) e decomposição

Uma dependência transitiva ocorre quando a chave determina um atributo não-chave, que determina outro atributo não-chave. Aqui, ID_Funcionario → ID_Departamento → Nome_Departamento. A 3FN exige que a relação esteja na 2FN e, para toda dependência funcional não trivial X → A, X seja superchave ou A seja atributo primo [2].

Vamos manter Funcionários (ID_Funcionario (PK), Nome, ID_Departamento (FK)) e criar Departamentos (ID_Departamento (PK), Nome_Departamento). O nome do departamento fica armazenado uma única vez.

Professores e salas: um determinante que não identifica a linha

Exemplo antes da regra

Considere que cada professor é responsável por uma única sala, mas pode ministrar várias disciplinas. A combinação professor-disciplina identifica cada aula:

Aulas com sala repetida por professor
ProfessorDisciplinaSala
AnaMatemáticaA101
BrunoHistóriaB202
AnaFísicaA101

A regra Professor → Sala determina a sala, mas Professor sozinho não identifica cada linha. Uma relação está na Forma Normal de Boyce-Codd (FNBC) quando todo determinante de dependência funcional não trivial é superchave [3].

Vamos decompor em Professores (Professor (PK), Sala) e Aulas (Professor (PK, FK), Disciplina (PK)). Sob as regras dadas, a junção recupera as linhas originais sem perda.

Médicos: listas independentes multiplicam combinações

Exemplo antes da regra

Um médico pode ter especialidades e idiomas falados que são independentes. Se o médico A tem duas especialidades e fala três idiomas, armazenar tudo na mesma relação pode produzir seis combinações:

Combinações redundantes entre especialidades e idiomas
MédicoEspecialidadeIdioma
ACardiologiaPortuguês
ACardiologiaInglês
ACardiologiaEspanhol
APediatriaPortuguês
APediatriaInglês
APediatriaEspanhol

A dependência multivalorada expressa valores independentes associados à mesma entidade. A 4FN exige que toda dependência multivalorada não trivial tenha como determinante uma superchave. Vamos separar em Médico_Especialidade (ID_Medico, Especialidade) e Médico_Idioma (ID_Medico, Idioma), além da tabela de médicos se ela tiver outros atributos [2].

Vendedores, empresas e produtos: cuidado com junções em cadeia

Exemplo conceitual antes da definição

Imagine uma relação que registra quais vendedores atendem quais empresas e quais produtos são negociados. As relações aos pares podem sugerir uma combinação que nunca existiu:

Relação original: triples válidos
VendedorEmpresaProduto
V1E1P1
V1E2P2
V2E1P2

As projeções por pares podem formar Vendedor-Empresa, Empresa-Produto e Vendedor-Produto. Ao reuni-las, é possível gerar a tupla (V1, E1, P2), que não estava nos dados originais. Essa tupla espúria mostra por que não basta decompor e presumir que o JOIN é seguro.

O que a 5FN exige

A Quinta Forma Normal (5FN), também chamada Forma Normal de Projeção-Junção (PJNF), trata de dependências de junção. Uma relação está na 5FN quando toda dependência de junção não trivial é implicada por suas chaves candidatas. A decomposição em três tabelas só é correta se a regra do negócio garantir a dependência de junção correspondente [1][2].

Erros comuns ao normalizar

  • Guardar listas delimitadas por vírgulas em uma coluna que precisa ser pesquisável individualmente.
  • Dividir atributos sem considerar como serão usados e quais são as regras do domínio.
  • Confundir chave primária com a única chave candidata possível.
  • Assumir que qualquer decomposição pode ser reconstruída sem tuplas espúrias.
  • Aplicar uma forma normal sem validar as dependências funcionais e de junção do negócio.
  • Normalizar sem considerar o contexto: pode reduzir anomalias, mas exigir mais junções; vamos equilibrar integridade, clareza e desempenho.

Como começar na área

  1. Desenhe entidades, atributos e relacionamentos com exemplos reais.
  2. Identifique chaves candidatas e escreva as dependências determinadas pelas regras de negócio.
  3. Verifique atomicidade e dependências parciais antes de avaliar formas mais rigorosas.
  4. Teste a decomposição com dados de exemplo e confira se JOINs preservam as linhas esperadas.
